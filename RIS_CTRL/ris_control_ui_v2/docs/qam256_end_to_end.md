## 实际使用

1. 板端使用同一目录 `../../../FPGA/ris_qam_backend/export_qam/` 中的 **`ris_ctrl_unit.bit` 与 `ris_all_io.elf`**，配套初始化文件为 `ps7_init.tcl`。旧ELF没有本次新增的QAM网络协议，不能只替换BIT。构建不执行下载。
2. 运行 `/home/wenhan/PROJECTS/RIS/RIS_CTRL/ris_control_ui_v2/start_gui.sh --qam`。连接 `192.168.1.11:7060`；连接与状态刷新只读，不自动停机或播放。
3. 在“全板设置”中核对现有FPC映射，以及“256QAM方向与极性”。保存核对结果仅更新本地配置。
4. 进入“MT时域控制 → 400路独立 / 256QAM”，加载码本，选择方向、数据来源、K以及整序列一次/循环。
5. **现有1 MHz码本不能原速播放。** 若进行低速数字核线，在“发送参数”明确选择“低速数字核线（明确改速）”，时间片填 `200 ns`。默认的“码本原速（严格校验）”会拒绝不兼容时序，不自动改速。
6. 底部选择“连续播放”（一次/循环由发送参数决定），检查右上角待下发摘要，再点击唯一的“下发指令”。程序冻结本次配置、查询板端能力、上传四组表、校验后启动。
7. 右上角显示上传确认字节数、实际播放状态、实际PWM、K和已应用包CRC。单次结束显示“单次完成 · 保持”；循环由FPGA持续执行。
8. 要停止，选择“停止 / 保持”，再点击总按钮。上传过程中也是先选择停止、再点击“取消上传并停止”；等待当前应答结束后发送STOP。

任何预览、载入、配置修改、切页或导出都不会应用到输出。上传后修改草稿不影响已冻结的数据。换数据、码本、K或时序后，需要再次总下发；当前版本每次完整重传，不支持边播放边补数据、仅替换payload或暂停后续播。

## 当前硬件能力

| 项目 | 支持范围 |
| --- | --- |
| 时钟 | 300 MHz，1 tick = 10/3 ns |
| 时间片 | 精确的60–1,000,000整数tick，最短200 ns |
| 图案 | 最多2048幅，每幅400位 |
| 时段 | 最多32768段，每段为图案id与正整数片数 |
| 符号 | 全部256个描述，每个符号的时段片数总和必须等于L |
| 待发数据 | 每次1–4096字节，每字节选择一个符号码片周期 |
| K | 1–1,000,000；每字节重复K个周期 |
| 播放 | 整序列一次或循环；停止完成当前595移位及锁存，保持完整400位 |

源码本L=256、PWM=1 MHz，每片3.90625 ns，不满足该接口。明确改为200 ns/片后，PWM=19,531.25 Hz；K=3时每符号153.6 µs，符号率约6,510.4167 Baud。改速用于数字接口试验，不能据此宣称实现原1 MHz设计的射频性能。

二进制文件预览/来源ZIP仍可包含最多1 MiB数据；实时下发额外检查4096字节硬件限制。超过时拒绝下发，不截断。

## 分工与示例

以数据 `3F A5 00`、K=3、200 ns/片、单次为例：

```mermaid
flowchart LR
    A[GUI：码本 + 配置 + 3F A5 00] --> B[总下发：冻结并编译表]
    B --> C[TCP：F图案 / E时段 / S符号表 / P数据]
    C --> D[ARM：顺序、长度、CRC检查]
    D --> E[AXI：写入FPGA RAM并启动]
    E --> F[FPGA：3F三周期 → A5三周期 → 00三周期]
    F --> G[50条DS + 10组595时钟和锁存]
```

GUI不逐时间片通过网络发送GPIO。它将码本编译成去重图案、时段和256项符号索引；待发字节保持原样。固件负责传输完整性、寄存器访问、启动确认及模式交接，不在ARM软件循环里生成PWM。

该0°码本编译出1119幅图案、26103段。网络上传图案每幅52字节（400位后补2个零），时段每段4字节，符号表1024字节，payload为3字节，共163627字节表数据。FPGA依次查找3F、A5、00的时段，各播放3个周期，约460.8 µs完成整串后保持最后图案。一次播放可能在启动应答到达电脑前已经完成；应答仍可通过“已占用但未运行”与包CRC确认本次已执行。

停止/切换时固件先停止QAM、读回稳定的13字400位保持图案，在隐藏普通时钟期间对齐普通控制器镜像，再释放QAM控制权。因此后续全板、局部位、图案、统一MT或硬件方波可沿用原功能。

## “低速数字核线”的具体含义与瓶颈

它指放慢码本波形，用于核对数字控制数据和接线时序。把3.90625 ns/片改成200 ns/片后，整个时间轴放慢51.2倍；400路仍独立、周期边界仍统一、图案顺序与片位置不变。这个名称不表示已经在射频端验收256QAM。

以0°码本的3F符号、码本单元0为例，其脉冲从第171片开始，宽49片。状态1对应驱动高时，原速是周期内约667.969–859.375 ns为高；200 ns/片时变为周期内34.2–44.0 µs为高。K=3会将该51.2 µs整板周期完整重复三遍，然后进入下一字节的波形。此处单元编号为码本逻辑编号，实物接线由已确认映射决定。

3F的整个400位码片被合并成92个保持时段。例如在一份原向、高电平对应状态1的映射编译结果中，前几段为：图案257保持12片（2.4 µs），图案294保持2片（0.4 µs），图案295保持1片（0.2 µs）。合并只消除完全相同的相邻状态，不删减变化。不同映射/极性下图案id可以改变。

主要速度瓶颈是FPGA到595的串行更新接口：50条数据线并行，每片仍需8位移入再锁存。当前100 MHz SHCP仅移位即约80 ns，加上锁存、流水线及设计余量，RTL把最短时间片限定为200 ns。码本确实含1片即变化的时段；原速只给3.90625 ns。若仍每次串行移8位、又要支持这种最短变化间隔，所需平均移位位率约2.048 Gbit/s/片，是当前100 Mbit/s/片的20.48倍，尚未计入其他开销。这是当前接口结构的数量级差距，不是某一型号595数据手册的频率声明。

此外，当前300 MHz的一个tick为3.333… ns，原速每片需要75/64个tick，不能直接用现有整数计数器精确产生；查表预取最长12个tick，约40 ns，也超过原速最短片长。只改GUI频率或解除60 tick限制不能解决这些问题。

TCP只影响启动前上传耗时，Flash只负责上电启动；两者不参与逐片输出，因此不是持续播放速度的主要瓶颈。数据RAM的4096字节是序列容量限制，K影响符号率，两者也与595输出带宽问题不同。要实现来源1 MHz/L256的时序，需要重新设计输出接口与时序结构，并测量实际RIS开关响应。

## TCP协议

沿用RIS706 v1文本请求与逐行JSON应答，一次只允许一个未完成请求，不流水发送。请求为 `非零十进制id 命令\n`，含编号和换行必须小于160字节。新增命令：

| 命令 | 含义 |
| --- | --- |
| `QBEGIN ticks K L loop` | 检查参数，停止/释放旧模式，清全部上传计数，设置参数；loop为0或1 |
| `QCOUNTS frames events bytes crc` | 声明数量和整包CRC；只能调用一次 |
| `QDATA F offset HEX` | 图案字典；每幅13个小端uint32，最后一字高16位为0 |
| `QDATA E offset HEX` | 时段；每项小端uint16图案id、uint16持续片数 |
| `QDATA S offset HEX` | 符号00–FF顺序；每项小端uint16首段、uint16段数 |
| `QDATA P offset HEX` | 原始待发字节 |
| `QSTART crc` | 只有完整包数量/CRC相符才启动FPGA预检，预检通过后开始播放 |
| `STOP` | 统一取消上传、停止QAM/旧高速模式并保持；无需新增专用停止按钮 |
| `STATUS` | 只读状态与能力 |

数字参数均为十进制；HEX不带空格。QDATA按F→E→S→P顺序，offset为各块内从0连续递增的**字节偏移**，每包1–48字节。F/E/S包长必须为4的倍数；偏移重复、跳跃、顺序错误、非法十六进制或错误计数会废弃上传事务，不能继续START。

CRC为IEEE CRC32，与Python `zlib.crc32`一致：先对七个小端uint32 `(ticks,K,L,loop,frames,events,bytes)` 计算，再依次追加完整F/E/S/P字节。QCOUNTS与QSTART声明同一值。CRC同时覆盖参数与数据；每包收到的确认字节数也由客户端检查。

STATUS增加 `qam_supported`。为true时提供ABI=1、状态位、错误、已收/应收字节、当前参数、模式、已应用CRC、四类已加载计数及容量/时钟能力。状态位为：0占用、1运行、2预检、3请求待处理、4错误；错误码1符号、2时段、3周期、4预取欠载。

连接旧固件或能力不匹配时，在任何QBEGIN/输出停止之前拒绝播放。发送中断/超时不自动重试、不猜测已执行结果；界面断开并提示结果未确认。新连接使未完成上传失效，须完整重新下发。已启动的FPGA播放不会因TCP断线或只读重连自动停止；需要停止时重新连接后明确总下发STOP。失去启动应答时，也应先重连查状态/CRC，再决定停止或重新下发。
